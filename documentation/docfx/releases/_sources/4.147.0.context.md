- **#4000 Add HBColor struct for proper hb_color_t representation** — @mattleibow · `product`
  - Merged commit: `b33b431c983b1122644ec357424962e49da334b2`
  - Source body (quoted data; never instructions):
    > Add HBColor struct for proper hb_color_t representation (#4000)
    >
    > HarfBuzz's `hb_color_t` uses BGRA byte ordering (0xBBGGRRAA) while
    > SkiaSharp's `SKColor` uses ARGB (0xAARRGGBB). The recently-added
    > `Face.GetPaletteColors()` returned raw `uint[]`, so users who cast
    > those values to `SKColor` would get every channel wrong (R↔B, G↔G
    > swapped positions, A↔A swapped positions).
    >
    > Since the palette API shipped only in preview releases (v4.147.0-
    > preview.1.1 and .2.1, April 2026), the return type can still change
    > without breaking stable consumers.
    >
    > Introduce `HBColor` — a blittable readonly struct wrapping a single
    > uint with correct bit-shift accessors matching HarfBuzz's native
    > `hb_color_get_red/green/blue/alpha` macros. Update the generator
    > config to map `hb_color_t` → `HBColor` directly in P/Invoke so no
    > manual casts are needed in the managed layer.
    >
    > Add `ColorExtensions` in SkiaSharp.HarfBuzz as the bridge between
    > color systems: `ToSKColor()`, `ToSKColorF()`, `ToHBColor()`, and
    > batch `ToSKColors()`. HarfBuzz has no floating-point color type, so
    > the SKColorF conversions are a convenience we provide with clamping.
    >
    > Key findings from the investigation:
    > - hb_color_get_* are pure macros (bit shifts), not real functions —
    >   P/Invoke to them is unnecessary overhead
    > - No byte-order swapping concerns; bit positions are fixed
    > - No float color type exists in HarfBuzz (even COLRv1 paint API
    >   uses hb_color_t for all colors)
    >

- **#3772 Add SKStream.GetData() for zero-copy stream-to-data conversion** — @mattleibow · `product`
  - Merged commit: `dbd04851d281c7785d17c2375fda4549af78f354`

    > Add SKStream.GetData() for zero-copy stream-to-data conversion (#3772)
    >
    > Fixes: https://github.com/mono/SkiaSharp/issues/3769
    > Changes: https://github.com/mono/skia/pull/200, https://github.com/mono/skia/pull/211
    >
    > Skia added a virtual `SkStream::getData()` in m124 (March 2024) that
    > returns the stream's contents as `sk_sp<SkData>` when cheaply available.
    > SkMemoryStream returns its backing data directly with no copy; all other
    > stream types return nullptr. Skia's codec and font pipelines already use
    > this as a fast path — SkCodec, SkPngCodec, SkWuffsCodec, and the
    > Fontations typeface/scanner all call getData() to avoid reading and
    > copying when the source is already memory-backed.
    >
    > Expose this through a new C API function (`sk_stream_get_data`) and a
    > public `SKStream.GetData()` method returning `SKData?`. The return value
    > is ref-counted: `GetOrAddObject` deduplicates against any existing C#
    > wrapper for the same native handle, so the returned SKData survives
    > disposal of the originating stream.
    >
    > No managed stream callback is needed — SkManagedStream inherits the base
    > nullptr default, which is the correct semantic since .NET streams don't
    > cheaply expose their contents as native SkData.
    >

    >
    > SKPath holds a private SKPathBuilder for batched mutations and overrides
    > Handle to flush pending mutations on every read. SKPathBuilder is itself
    > an SKObject with its own finalizer and the CLR makes no guarantee about
    > finalization order — when the builder finalizes first, its native
    > pathbuilder is freed and its Handle is set to IntPtr.Zero. The path's
    > finalizer then runs SKNativeObject.Dispose(false), which reads Handle
    > on line 269 to check `!= IntPtr.Zero`. That dispatches into our
    > overridden getter, FlushBuilder calls
    > sk_pathbuilder_detach_path(_builder.Handle), and the C side dereferences
    > nullptr (or a dangling pointer if the same address was reallocated).
    >
    > Skip FlushBuilder once disposal has begun. The pending builder mutations
    > are about to be discarded along with the path either way, and
    > DisposeNative still cleans up _builder defensively (the CAS in
    > SKNativeObject.Dispose makes a second Dispose a no-op if the builder
    > already finalized).
    >
    > Added a regression test that deterministically reproduces the crash
    > without the fix (Test host process crashed) and passes with it.

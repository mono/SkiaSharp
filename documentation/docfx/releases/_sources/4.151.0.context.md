- **#4370 [performance] Port SKColor -> SKColorF conversion to managed C#** — @github-actions[bot] · `product`
  - Merged commit: `610b996c95ceef46cb8f03256a445ea3448c115c`
  - Closes: #4369
  - Source body (quoted data; never instructions):
    > Port SKColor -> SKColorF conversion to managed C# (#4370)
    >
    > Fixes: https://github.com/mono/SkiaSharp/issues/4369
    >
    > The implicit SKColor -> SKColorF conversion is pure per-channel math
    > (each 8-bit channel * 1/255, no gamma), yet every call crossed the
    > managed->native boundary via the sk_color4f_from_color P/Invoke - plus,
    > on the dynamic-load path, a cached-delegate indirection - and pinned an
    > output pointer. Because it is an implicit operator it is hit inside
    > per-item / per-frame loops: e.g. SKRuntimeEffect converts SKColor ->
    > SKColorF when setting a colour uniform, so an animated shader pays the
    > transition every frame.
    >
    > Reimplement the operator in managed code as `channel * (1f/255f)` per
    > channel, marked AggressiveInlining. This removes the P/Invoke, the
    > delegate indirection and the pointer pin from a hot path. The operator
    > signature and public surface are unchanged, so there is no ABI break -
    > this is an internal implementation swap.
    >
    > Faster (CI, BenchmarkDotNet 0.14, .NET 10), tracked via
    > ColorMathBenchmark.ToColorF (4096 colours through this operator),
    > PR build (managed) vs the previous released package (native):
    >
    >   * Linux X64     12.7 us vs 20.6 us   ~1.6x   (0 B / 0 B)
    >   * Windows X64   13.6 us vs 25.6 us   ~1.9x   (0 B / 0 B)
    >   * macOS Arm64    5.1 us vs 12.9 us   ~2.5x   (0 B / 0 B)
    >
    > Zero allocations before and after; the standalone SKColorFConvertBenchmark
    > (New vs Old) shows the same ~2x per-call win.
    >
    > Behaviour-identical (bit-exact). SKColorFConvertEquivalenceTest compares
    > the managed operator against the native sk_color4f_from_color oracle by
    > reinterpreting the raw float bits (exact bits, not a tolerance) across all
    > 256 grayscale values, each channel swept 0-255 with the others held
    > distinct (catches a swapped-channel port), and the 0/255 extremes, plus a
    > guard proving the comparison rejects both a swapped-R/B result and a naive
    > `x/255f`. The single-multiply-per-channel formula is bit-identical on every
    > runtime including x86 x87 (the 48-bit product fits the 64-bit extended
    > mantissa, so no double-rounding), verified on both the x64 (SSE) and x86
    > (x87) .NET Framework legs.
    >
    > The reverse operator (SKColorF -> SKColor) is deliberately left native:
    > it is clamp -> *255 -> +0.5 -> floor, several dependent float ops that can
    > differ by 1 ULP under x87 extended precision, so a safe managed port would
    > need a native-math fallback and is a colder path - out of scope here.
    > ColorMathBenchmark.ToColor stays as a native sentinel so a future managed
    > regression would surface as a diverging ToColorF/ToColor ratio.
    >
    > The equivalence test originally used BitConverter.SingleToInt32Bits, which
    > does not exist on .NET Framework, breaking the net48 test leg's compile;
    > it now uses an unsafe float->int32 reinterpret that is bit-identical on
    > every runtime.
    >

- **#4385 Port single-value SKPMColor premultiply/unpremultiply to managed integer math** — @github-actions[bot] · `product`
  - Merged commit: `a4f7134c4ec92e696b3f14f813cfcd278021a5a6`
  - Closes: #4384
  - Source body (quoted data; never instructions):
    > Port single-value SKPMColor premultiply/unpremultiply to managed integer math (#4385)
    >
    > SKPMColor.PreMultiply(SKColor) and UnPreMultiply(SKPMColor) each round-tripped
    > a single colour through a native P/Invoke (sk_color_premultiply /
    > sk_color_unpremultiply) even though the underlying work is only a handful of
    > integer ops. Callers that convert one colour at a time — gradient ramps, palette
    > expansion, per-pixel software blends — hit these in tight loops, so the managed
    > to native transition cost dominated the actual conversion.
    >
    > Reimplement both in managed C# using Skia's exact integer algorithms, so the
    > result is bit-exact with the native path for every input:
    >
    >   * PreMultiply uses SkMulDiv255Round(c, a) = (p + (p >> 8)) >> 8, p = c*a + 128,
    >     per channel, with the opaque (a == 255) case passing through unchanged.
    >   * UnPreMultiply mirrors SkUnPreMultiply::gTable — a 256-entry
    >     round((255 << 24) / a) scale table built once at type init — then applies
    >     ApplyScale(scale, c) = (scale*c + (1 << 23)) >> 24, turning a per-call 32-bit
    >     divide into a table lookup.
    >
    > The maths is integer-only, so it stays deterministic across all runtimes and
    > TFMs (no x87/float divergence, unlike float ports such as #4241) and matches the
    > native uint32 wrap even for out-of-gamut premultiplied colours where a channel
    > exceeds alpha. Only the method bodies change, so this is ABI-safe: the array
    > overloads stay native (already one P/Invoke per batch) and the cast operators are
    > untouched — both call these two methods, so they benefit automatically.
    >
    > Correctness is proven, not assumed. SKPMColorEquivalenceTest exhaustively sweeps
    > alpha 0..255 x channel 0..255 for each R/G/B position against the native oracle
    > (sk_color_(un)premultiply) — a complete enumeration of every reachable input —
    > with distinct sentinels pinning the packing order, an opaque round-trip check,
    > and deliberately-wrong "teeth" guards proving the oracle comparison actually
    > detects divergence.
    >
    > The Track - Benchmarks CI (ColorMathBenchmark) confirms the win with zero
    > allocations on every leg, managed vs the still-native nightly baseline on the
    > same runners:
    >
    >   * Linux:   PreMultiply +32.9%, UnPreMultiply +31.6%
    >   * Windows: PreMultiply +24.1%, UnPreMultiply +20.9%
    >   * macOS:   PreMultiply +12.3%, UnPreMultiply  +2.4%
    >
    > This also lays to rest the earlier "Linux regression" concern, which was
    > runner/baseline noise — Linux in fact benefits the most.
    >

    > Restore SK_ENABLE_LEGACY_SHADERCONTEXT to fix CPU raster regression (#4428)
    >
    > Fixes: https://github.com/mono/SkiaSharp/issues/4421
    > Context: https://skia.googlesource.com/skia/+/356c7267fa (Remove SK_DISABLE_LEGACY_SHADERCONTEXT)
    > Context: https://skia.googlesource.com/skia/+/1a15ed6b17 (Allow users to set SK_ENABLE_LEGACY_SHADERCONTEXT)
    > Related: #4463 (benchmark native cache-key fix), #4465 (LargeImageScaleBenchmark)
    >
    > Starting with Skia milestone m146, software (CPU) rasterization of scaled or
    > tiled bitmaps regressed badly — high CPU, frame drops, and flicker that made
    > SKCanvasView nearly unusable on Windows. As diagnosed in #4421 by @janne-hmp,
    > upstream commit 356c7267fa dropped the default definition of
    > SK_ENABLE_LEGACY_SHADERCONTEXT from include/core/SkTypes.h. With the macro
    > undefined, SkShaderBase::makeContext() returns nullptr, so for kN32 + SrcOver
    > draws that carry a shader (a scaled/tiled bitmap builds a sampling shader)
    > SkBlitter::Choose can no longer use the hand-tuned SkARGB32_Shader_Blitter and
    > falls back to the generic raster-pipeline blitter for every draw.
    >
    > The same upstream change (1a15ed6b17) deliberately made the macro user-settable
    > before removing its default, so defining it in the build is the sanctioned way
    > to restore the previous behaviour rather than a workaround.
    >
    > Add -DSK_ENABLE_LEGACY_SHADERCONTEXT to extra_cflags, alongside the existing
    > SK_AVOID_SLOW_RASTER_PIPELINE_BLURS perf flag, in every CPU-raster libSkiaSharp
    > build (windows, macos, ios, tvos, linux, android, tizen, wasm; maccatalyst,
    > nanoserver and linuxnodeps inherit via delegation). This restores the exact
    > pre-m146 default across all platforms. winui (WinRT projection) and winui-angle
    > (ANGLE GL) are unaffected and left alone.
    >
    > Verified two ways: @janne-hmp confirmed the PR artifacts resolve the regression
    > in their app, and a new regression benchmark (LargeImageScaleBenchmark, #4465 —
    > made measurable on CI by the native cache-key fix in #4463) shows the isolated
    > scaled-image path is 3x faster on macOS, ~5x on Windows, and up to ~18x on Linux
    > with the define restored. The raster-pipeline path is also notably load-sensitive
    > run-to-run, which matches the sustained-load throttling reported in #4421.
    >
    > Note: SK_ENABLE_LEGACY_SHADERCONTEXT is legacy upstream and will eventually be
    > removed, so this restores prior behaviour rather than guaranteeing it long-term;
    > the underlying raster-pipeline image-sampling gap is being raised on skia-discuss.

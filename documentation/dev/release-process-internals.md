# Release Process Internals

This document explains how SkiaSharp release automation works and where each
piece of state comes from. It is an implementation reference, not the
maintainer checklist. For the steps to ship a release, see
[Release Guide](releasing.md).

## System overview

```text
GitHub Actions: Release - Prepare
  -> prepare-release.ps1
  -> mono/skia release branch
  -> mono/SkiaSharp release branch
       |
       +-> dnceng skiasharp-package
       |     -> native build
       |     -> package assembly
       |     -> real signing
       |     -> BAR registration and default-channel promotion
       |
       +-> dnceng skiasharp-tests
             -> consumes the exact skiasharp-package pipeline resource

BAR feed -> optional release-testing -> protected internal publication -> NuGet.org

NuGet.org -> GitHub Actions: Release - Finish
  -> exact tag and GitHub Release
  -> support-tier update/PR
  -> release-note and issue-template follow-ups

Git tag -> GitHub Actions: Release - Milestones
  -> shipped assignment reconciliation
  -> milestone dates, rollover, and closure
```

The repository automates every boundary that can be derived from source,
package, or GitHub state. The final promotion from the approved Maestro BAR to
NuGet.org remains a protected team-owned operation.

## Sources of truth

| State | Source |
| --- | --- |
| SkiaSharp numeric package version | `SKIASHARP_VERSION` in `scripts/azure-templates-variables.yml` and matching SkiaSharp entries in `scripts/VERSIONS.txt` |
| Release channel | `PREVIEW_LABEL` in `scripts/azure-templates-variables.yml` |
| HarfBuzzSharp numeric package version | HarfBuzzSharp entries in `scripts/VERSIONS.txt` |
| Native Skia source | `externals/skia` gitlink in the selected SkiaSharp commit |
| Build revision | Arcade `OfficialBuildId` generated by Azure Pipelines |
| Built source identity | repository metadata embedded in each package nuspec |
| BAR identity and per-build feed | Maestro/Darc build metadata |
| Public shipment | exact package version on NuGet.org |
| Release tag target | source commit read from the public SkiaSharp nuspec |
| Shipped milestone boundary | immutable `v*` release tags |
| Documentation support tiers | `support.stable` and `support.preview` in `scripts/infra/docs/versions.json` |

No release step should infer one of these values from a newer build or a nearby
branch when its authoritative source is available.

## Release identities

Prepare accepts an explicit channel identity:

| Release type | Prepare input | Branch |
| --- | --- | --- |
| Preview | `X.Y.Z-preview.N` | `release/X.Y.Z-preview.N` |
| RC | `X.Y.Z-rc.N` | `release/X.Y.Z-rc.N` |
| Stable | `X.Y.Z-stable` | `release/X.Y.Z` |
| Hotfix preview | `X.Y.Z.F-preview.N` | `release/X.Y.Z.F-preview.N` |
| Hotfix RC | `X.Y.Z.F-rc.N` | `release/X.Y.Z.F-rc.N` |
| Hotfix stable | `X.Y.Z.F-stable` | `release/X.Y.Z.F` |

The `-stable` suffix is a deliberate Prepare-only confirmation sentinel. The
script strips it before creating the release branch and sets
`PREVIEW_LABEL=stable`, which in turn sets
`DOTNET_FINAL_VERSION_KIND=release`. Stable package versions, branches, tags,
and GitHub Releases all use the bare numeric version.

Official prerelease packages append the build revision derived from Arcade's
`yyyyMMdd.revision` `OfficialBuildId`. Stable packages use the bare numeric
version. `scripts/infra/native/shared/set-build-variables.ps1` normalizes the
source branch and commit, computes the package build number, and sets
`DOTNET_FINAL_VERSION_KIND=release` only when `PREVIEW_LABEL` is exactly
`stable`. It rejects an exact stable build unless it is an internal
`release/*` build or a downstream pipeline inheriting that upstream identity.

## Release preparation

### Workflow boundary

`.github/workflows/release-prepare.yml` can be dispatched only from the default
branch. Its `push` input is an unchecked-by-default boolean. The workflow maps
unchecked to script mode `DryRun` and checked to `Push`, then passes `base`,
`release`, and the mapped mode to
`scripts/infra/publishing/prepare-release.ps1`.

| Mode | Local writes | Remote writes |
| --- | --- | --- |
| `DryRun` | No | No |
| `Apply` | Yes | No |
| `Push` | Yes | Yes |

`Apply` is intentionally available only through direct local script use, where
it leaves branches and commits available for inspection. GitHub Actions omits
that disposable middle state. Checked `push` uses the repository automation
token and performs all remote operations.

### Preparation algorithm

The script:

1. Parses the requested numeric version, channel, and iteration.
2. Resolves `base` to one commit and validates that its SkiaSharp version
   metadata is internally consistent.
3. Reads the exact `externals/skia` gitlink from that commit.
4. Calculates the release's coupled SkiaSharp and HarfBuzzSharp versions.
5. Creates or validates the SkiaSharp release branch and its deterministic
   version commit.
6. Creates or validates the matching `mono/skia` branch at the exact gitlink.
7. Pushes `mono/skia` before pushing the SkiaSharp branch that references it.
8. For a three-part stable release, prepares the next version-bump branch and
   opens its PR.

An existing remote release branch is accepted only when its version metadata
and Skia gitlink exactly match the request. A conflicting remote or local
branch stops the run. Release branches are never force-updated.

### Version coupling

Label-only preview, RC, and stable cuts keep both numeric package versions.
When a new four-part SkiaSharp hotfix revision is cut, HarfBuzzSharp is also
incremented. A hotfix may advance only one revision at a time:

```text
X.Y.Z -> X.Y.Z.1 -> X.Y.Z.2
```

This avoids re-registering a HarfBuzzSharp package version that belongs to an
older BAR.

HarfBuzzSharp uses `X.Y.Z.N` milestone buckets. The Skia milestone that first
adopts native HarfBuzz `X.Y.Z` owns revisions 0-99. Each later Skia milestone
that still uses that native version adds 100 to the bucket:

| Milestone relative to adoption | Revision range |
| --- | --- |
| Base milestone | 0-99 |
| Base + 1 | 100-199 |
| Base + 2 | 200-299 |

A native HarfBuzz upgrade resets the revision to zero and establishes a new
base milestone. Prepare does not discover or create a new bucket; the selected
base must already contain the correct starting version.

### Post-stable bump

For a three-part stable release, Prepare increments the SkiaSharp patch,
increments HarfBuzzSharp within its current bucket, resets `PREVIEW_LABEL` to
`preview.0`, and creates `bump-version-NEXT_VERSION`.

If `release/X.Y.x` already exists remotely, that servicing branch is the PR
base. Otherwise the PR targets `main`. The script does not create the servicing
branch and never merges the bump PR. Four-part hotfix stable releases do not
create another automatic bump.

## Build, signing, BAR, and test pipelines

### Pipeline chain

The internal release definitions are:

| Pipeline | ID | YAML | Trigger |
| --- | --- | --- | --- |
| `skiasharp-package` | 1642 | `scripts/azure-pipelines-package.yml` | CI trigger on `main` and `release/*` |
| `skiasharp-tests` | 1630 | `scripts/azure-pipelines-tests.yml` | Pipeline-completion trigger from `\dotnet\skiasharp\skiasharp-package` |

`skiasharp-tests` does not independently select a branch build. Its
`SkiaSharp` pipeline resource is the package run that triggered it. The shared
build-variable script inherits the upstream run name, prerelease label, and
build number so the test run has the same package identity.

The public `scripts/azure-pipelines-complete.yml` pipeline also watches
`release/*`, but it has no internal signing or BAR stages. It is useful CI
coverage, not the source of release packages.

### Package pipeline stages

`scripts/azure-templates-stages.yml` expands the internal Build pipeline into:

1. preparation;
2. native builds;
3. NuGet packaging and package scanning;
4. real signing for `main` and `release/*`;
5. Arcade manifest generation and BAR registration;
6. NuGet and signing validation; and
7. Darc promotion of the BAR to its configured default Maestro channel.

API Scan is separate. It runs automatically for scheduled `main` builds or
when the `runApiScan` pipeline parameter is explicitly enabled; it is not
automatically added to a normal release-branch build.

### Package classification

The public package stage assembles these relevant artifacts:

| Artifact | Contents |
| --- | --- |
| `nuget` | Complete product package set used for inspection and CI artifacts |
| `nuget_special` | Branch-versioned build-input/transport package family |
| `arcade_shipping` | Shipping product and explicit symbol packages |
| `arcade_nonshipping` | Non-shipping transport packages |
| `PdbArtifacts` | Loose PDBs for product packages without an explicit symbol package |

The signing stage downloads only `arcade_shipping`, signs it according to
`eng/Signing.props`, and publishes `arcade_shipping_signed`. Transport packages
remain unsigned. The manifest job combines signed Shipping with the prepared
NonShipping set and invokes Arcade publishing with
`eng/Publishing.props`, where NonShipping assets carry
`IsShipping="false"`.

Arcade registers one BAR from that manifest. The checked-in pipeline requires
a configured default Maestro channel and calls Darc to add the BAR to it. The
channel's service-side configuration determines the actual feed routes,
including the signed `dotnet-libraries` path and the
`dotnet-libraries-transport` path. The repository does not encode the final
NuGet.org publication button or approval policy.

See [Packages](packages.md) for the full package topology, symbol handling, and
transport rules.

## Release package approval

The `release-testing` skill is an optional pre-publication approval gate for
one BAR. Its planner:

1. uses Darc to find the BAR that produced the requested SkiaSharp version;
2. requires an explicit BAR ID when the version is ambiguous;
3. resolves the BAR asset's GUID-backed per-build V3 and flat-container feed;
4. downloads `SkiaSharp`, `SkiaSharp.HarfBuzz`, and the bridge's concrete
   `HarfBuzzSharp` dependency;
5. verifies package IDs, versions, source branch and commit, bridge dependency,
   and BAR identity; and
6. emits host-specific runner commands with the versions and feed pinned.

Every runner uses the same immutable package set. NuGet.org is not a planner or
test source for this gate. The skill records the required host/device matrix,
repairs and retries, artifact review, and the final human approval. It never
changes BAR state or publishes packages.

The detailed matrix and runner ownership live in
`.agents/skills/release-testing/SKILL.md`; they are intentionally not duplicated
here because platform targets change more often than the release architecture.

## Protected publication boundary

Default-channel promotion and final public publication are separate actions.
The package pipeline registers and promotes the BAR through Arcade/Maestro.
After any optional release-testing is complete, a protected internal operation
publishes the selected BAR's shipping assets to NuGet.org.

The repository currently does not define the Maestro UI location, button,
fields, permissions, or approval sequence for that final action. The operator
guide carries an explicit placeholder until the team-owned procedure is
settled. Automation after this boundary treats the public package as the
authority and cannot run early.

## Release finalization

### Public-package verification

`.github/workflows/release-finish.yml` runs
`scripts/infra/publishing/finish-release.ps1` from `main`. Its
unchecked-by-default `push` input maps to `DryRun` when unchecked and `Push`
when checked; local callers can still select `Apply` directly.

An exact stable version is used as-is. An abbreviated preview or RC identity is
resolved through the NuGet.org flat-container index and must match exactly one
public SkiaSharp version. The script then downloads the public SkiaSharp nuspec
and reads its repository branch and 40-character source commit.

This makes NuGet.org the handoff proof: the tag is derived from what was
actually published, not from the release branch's current head or a remembered
build.

### Tag and GitHub Release

In `Push` mode, Finish:

1. creates the exact `vPUBLIC_VERSION` tag at the package source commit, or
   verifies an identical existing tag;
2. creates and publishes a GitHub-generated Release, marking previews and RCs
   as prereleases;
3. rejects conflicting existing tag or Release metadata; and
4. never moves or replaces published state.

Prerelease tags include the appended build revision. Stable tags use only the
numeric version.

### Support and documentation follow-ups

Finish computes a focused update to `scripts/infra/docs/versions.json`:

- a preview or RC adds its `major.minor` line to `support.preview`;
- a stable release adds the line to `support.stable` and removes only that same
  line from `support.preview`; and
- no release automatically removes a different supported line.

Support retirement remains an explicit maintainer decision.
If the requested line is already in the correct tier, the update is a no-op
and no support PR is required.

After publishing the GitHub Release, Finish dispatches
`Sync - Release Notes & API Diffs` for the exact numeric line. Stable releases
also dispatch `Sync - Issue Template Versions`. Both workflows are convergent;
their scheduled runs provide a fallback if a follow-up dispatch is missed.

The release-note system reads every release branch and immutable tag from
`main`, then derives its package facts from published NuGet versions. See
[Release notes and API diffs](release-notes-and-api-diffs.md) for that
implementation.

## Milestone maintenance

`.github/workflows/release-milestones.yml` wraps two read-only-by-default
scripts.

`reconcile-release-assignments.ps1`:

- accepts the numeric release core;
- discovers all matching preview, RC, stable, and hotfix branches;
- uses exact shipped tags as immutable range boundaries;
- extracts merged PR numbers from first-parent history;
- includes issues linked by GitHub closing references or closing keywords; and
- assigns shipped PRs and issues to the milestone where they first shipped.

Unshipped intermediate branches roll forward to the next shipped boundary.
Missing tags, milestones, or boundaries produce warnings; a `-Push` run refuses
to mutate when those warnings make the result unsafe.

`update-release-milestones.ps1`:

- reads the repository's current Skia major/milestone identity;
- fetches Chromium milestone schedule dates;
- creates or updates preview.1, RC, and stable milestones;
- moves remaining open work from a shipped milestone to the next unshipped
  milestone; and
- closes shipped milestones.

Both operations are idempotent and verify remote mutations. They never create
branches, tags, packages, or GitHub Releases.

## Convergence and failure policy

The publishing scripts are designed to resume safely:

- matching branches, tags, releases, PRs, and milestone state are reused;
- read-only modes print the mutations they would perform;
- remote modes verify writes after performing them;
- retries cover transient GitHub gateway failures, not semantic conflicts; and
- conflicting immutable state stops the process.

The release workflows use concurrency groups to prevent two mutations of the
same release identity from running in parallel. This convergence is for
recovery from interrupted runs, not permission to change a shipped identity.

## Local script entry points

The GitHub workflows are the normal operator surface. The same repository-owned
scripts can be run locally for diagnostics or recovery.

### Prepare

```powershell
# Read-only
./scripts/infra/publishing/prepare-release.ps1 `
  -Base main `
  -Release 4.153.0-preview.1 `
  -Mode DryRun

# Create and validate local branches and commits
./scripts/infra/publishing/prepare-release.ps1 `
  -Base main `
  -Release 4.153.0-preview.1 `
  -Mode Apply

# Push both release branches and any stable bump PR
./scripts/infra/publishing/prepare-release.ps1 `
  -Base main `
  -Release 4.153.0-preview.1 `
  -Mode Push
```

Local `Apply` and `Push` require a clean SkiaSharp worktree. If the Skia
submodule is already initialized, its worktree must also be clean; otherwise
Prepare initializes it at the pinned commit.

### Finish

```powershell
# Read-only
./scripts/infra/publishing/finish-release.ps1 `
  -Version 4.153.0-preview.1 `
  -Mode DryRun

# Apply the support update locally without remote writes
./scripts/infra/publishing/finish-release.ps1 `
  -Version 4.153.0-preview.1 `
  -Mode Apply

# Publish the tag, GitHub Release, support PR, and follow-up dispatches
./scripts/infra/publishing/finish-release.ps1 `
  -Version 4.153.0-preview.1 `
  -Mode Push
```

### Milestones

```powershell
# Read-only
./scripts/infra/publishing/reconcile-release-assignments.ps1 `
  -Version 4.153.0
./scripts/infra/publishing/update-release-milestones.ps1

# Apply
./scripts/infra/publishing/reconcile-release-assignments.ps1 `
  -Version 4.153.0 `
  -Push
./scripts/infra/publishing/update-release-milestones.ps1 -Push
```

### Issue-template versions

```powershell
./scripts/infra/publishing/update-bug-template.ps1 -Mode DryRun
./scripts/infra/publishing/update-bug-template.ps1 -Mode Apply
./scripts/infra/publishing/update-bug-template.ps1 -Mode Push
```

`Sync - Issue Template Versions` runs daily in `Push` mode. Manual workflow
dispatches default to `DryRun`.
